# 六大工程能力的作用与原理说明

> 本文档说明 RAG、Harness 工程、Context 工程、Prompt 工程、Loop 工程、长期记忆六项能力的引入作用，通过"引入前 vs 引入后"的对比阐明每项能力解决的根本问题及其工作原理。

> ⚠️ **说明（2026-08-05）**：文中出现的量化比例（如"20-30%""~60%→~90%+""~95%""60-70%"）多为**工程估算值**。其中部分已由 `docs/08-verification-test-report.md` 给出实测结果（如滑动窗口 token 节省实测 ~72%），引用时以实测为准；未经实测的估算值请勿当作基准结论。

---

## 一、RAG（检索增强生成）

### 引入前的问题

LLM 的知识来源于训练数据，存在两个根本限制：

1. **知识截止日期**：模型只知道训练截止日前的信息，无法获取新发布的政策通知、学期最新公告等动态内容。
2. **幻觉问题**：当用户询问模型不确定的细节时（如"奖学金评定的具体绩点门槛是多少""心理咨询中心的预约电话是多少"），模型倾向于生成听起来合理但实际错误的内容。

**典型表现**：
- 用户问"我们学校图书馆研讨间预约需要几个人"→ 模型根据通用大学经验猜测回答，答案可能与本校规则完全不符
- 用户问"奖学金申请截止日期"→ 模型编造一个日期，用户照此准备材料却发现已过期
- 一般而言，未引入 RAG 的 Agent 在校园特定政策问题上的准确率不超过 40%，且用户无从判断回答是否可信

### 引入后的效果

RAG 将 LLM 的"记忆检索"替换为"外部知识库检索"，LLM 只需根据检索结果组织语言，不再依赖参数记忆回答具体事实。

**工作原理**：
```
用户查询 → 向量化 → 在百炼知识库中检索相似文档块
    → 检索结果注入 messages（作为 ToolResult）
    → LLM 基于检索内容生成回答，并标注参考来源
```

**三级质量优化**：

**① 查询改写（Query Rewriting）**
- 问题：用户说"图书馆预约"，这 5 个字的向量化结果与知识库中"图书馆研讨间预约规则及注意事项"的相似度并不高
- 方案：先用 LLM 将原始查询扩展为语义更丰富的形式，再向量化检索
- 效果：查询"图书馆预约"→ 改写为"图书馆研讨间预约规则申请流程注意事项人数限制"，向量相似度显著提升，Top-3 文档召回更准确

**② Rerank 重排序**
- 问题：向量相似度是粗排，前 10 个候选文档中排第 1 的不一定语义最相关
- 方案：使用 DashScope Rerank 模型对每个候选文档与查询做交叉编码评分，精排后取 Top-3（`rerank-top-n=3`）
- 效果：相比纯向量检索，Rerank 能将真正相关的文档从第 5-7 位提升到第 1-2 位，最终答案的相关性提高约 20-30%（**估算值**）

> ⚠️ **实测说明（2026-08-05，详见 `docs/08-verification-test-report.md` §6.5.2）**：对当前 DashScope pipeline 检索端点实测（12 条查询），`enableReranking=false` 与默认配置返回的排序与得分**完全一致**（0/12 条有差异），说明该 pipeline **始终执行其配置的 qwen3-rerank**。因此：
> - 本项目检索链路实际**始终经过重排**，属平台默认能力，而非可开关的优化步骤；
> - `enable-reranking` 配置项在当前 pipeline 配置下**不生效**；
> - "20-30%"为估算值，且无法通过该端点开关 A/B 验证。

**③ 混合检索**
- 问题：纯向量检索对精确服务名称（如"图书馆研讨间预约""奖学金材料预审"）匹配度不稳定
- 方案：同时执行关键词精确匹配（products 表 LIKE 查询），精确匹配结果以高优先级与向量结果合并
- 效果：用户询问特定服务时，精确匹配路径在毫秒内命中，不依赖向量相似度，确保服务基本信息的 100% 准确返回

**引入 RAG 后的核心变化**：LLM 从"凭记忆猜答案"变为"基于文档事实作答"，并在回答末尾附加参考来源（`**参考来源：** - 奖学金政策全览`），用户可自行核实，可信度从模糊变为可追溯。

## 二、Prompt 工程

### 引入前的问题

LLM 是一个通用模型，在没有明确指令约束的情况下，它的行为完全由当前消息决定：

1. **职责边界不清**：一个没有约束的 Agent 会尝试回答所有问题，包括它能力范围之外的（如直接回答政策问题但给出错误信息，而不是调用知识库工具）
2. **工具选择不准**：面对"取消我的预约"，模型可能直接发起取消操作，而不是先查询用户有哪些记录让用户确认
3. **边界场景失控**：模型遇到"你好"这类非业务消息时，可能错误地路由到某个子 Agent；遇到"取消我的预约然后投诉一下"这类多意图消息时，行为不可预测
4. **幻觉执行**：工具调用失败后，模型可能编造"已成功取消记录"的回答

**量化影响**：未经 Prompt 工程的 Agent，在路由准确率和工具选择顺序上的错误率通常在 30-50%，复杂边界场景下更高。

### 引入后的效果

Prompt 工程通过四个层次将模型行为约束在设计范围内：

**① 结构化 System Prompt（角色/流程/约束）**

每个 Agent 的 System Prompt 包含"角色定义 → 核心能力 → 工作流程 → 约束边界"四段式结构。

原理：LLM 在处理每次请求时，System Prompt 始终作为最高权重的上下文。明确的角色定义让模型"知道自己是谁"，详细的约束（如"只有工具明确返回成功才告知用户成功"）消除了幻觉执行的空间。

例如，order-agent 的约束段明确写明：
```
不要编造办理成功结果；只有工具明确返回成功时，才能告知用户办理成功
绝对不允许查询、修改或取消其他用户的办理记录
```
这两条约束将 LLM 的主动编造倾向和越权操作倾向降低到接近零。

**② Few-shot 示例注入（边界案例）**

在 System Prompt 末尾注入 5-6 条边界案例，让模型"见过"模糊场景如何处理。

原理：LLM 是 in-context learner，看到具体示例后的泛化能力显著强于纯文字描述。"用户说'取消我的预约' → 先查询记录列表让用户确认编号，再取消"这条示例，让模型在遇到类似场景时直接模仿示例行为，而不是根据通用知识自由发挥。

**③ 工具选择引导**

工作流程中明确列出"意图 → 工具"的对应关系（共 7 种意图 × 对应工具），LLM 不再需要从 13 个工具的 description 中自行推断哪个最合适。

原理：将工具选择从"检索问题"转化为"映射问题"，减少 LLM 的推理负担，工具调用准确率从通用推理的 ~60% 提升到明确映射的 ~90%+。

**④ Schema 注入（BeanOutputConverter）**

对于需要结构化输出的场景（EvaluationClassifierNode、PlannerNode），通过 `BeanOutputConverter.getFormat()` 自动生成 JSON Schema 注入 Prompt：

```json
{
  "user": "string（用户ID）",
  "complaint": "string（yes | no）",
  "satisfaction": "integer（0-5）",
  "summary": "string（核心诉求）"
}
```

原理：LLM 看到明确的 Schema 约束后，生成合规 JSON 的成功率从自由输出的 ~70% 提升到约 95%，即使偶尔格式不符，也有降级逻辑保底（存储原始文本）。

## 三、Context 工程

### 引入前的问题

一个没有上下文管理的 Agent 每次请求都是"失忆状态"：

1. **无多轮记忆**：用户第一句说"我是张三，userId 是 10001"，第二句说"帮我预约图书馆"，Agent 不记得第一句，要求用户重新提供 userId
2. **上下文丢失**：在 Plan-Execute 场景中，PlannerNode 生成的计划无法传递给 ExecutorNode（两者是不同的 NodeAction，无共享状态）
3. **信息过载**：多轮对话后，messages 列表可能累积 50+ 条消息，超过 LLM 的有效注意力范围（即使在 context window 内，过长的历史也会稀释当前意图的权重）
4. **身份传递断裂**：Supervisor 知道用户的 userId，但通过 A2A 转发给子 Agent 时，userId 信息没有对应的传递机制

### 引入后的效果

Context 工程通过五个机制构建立体化的上下文管理体系：

**① Checkpoint 状态恢复**

使用 `MemorySaver + RunnableConfig.threadId(chatId)` 持久化每轮图状态。同一 `chat_id` 的连续请求，Graph 自动从上次状态恢复，messages 历史、执行计划、工具调用结果均保留。

原理：`MemorySaver` 将 `OverAllState` 以 `Map<threadId, Checkpoint>` 形式存储在 JVM 内存中。每次 `fluxStream(input, runnableConfig)` 时，框架先从 Saver 读取 `threadId` 对应的历史状态，与本次 input 合并后执行。这使得"多轮对话"在 Agent 视角成为一个连续执行的长任务。

**② Memory 主动注入（个性化上下文）**

`MemoryInjectNode` 在每次 ReactAgent 推理前，主动查询 Mem0 获取用户历史偏好，以 `SystemMessage` 形式注入上下文最前端。

注入前：LLM 只知道当前消息，无法做个性化推荐
注入后：LLM 看到"该用户常在下午预约，偏好线上办理"，会主动在预约建议中体现这些偏好，无需用户每次重新说明

这里有一个关键设计：注入的是 `SystemMessage` 而非 `UserMessage`，因为 LLM 对 SystemMessage 的注意力权重更高，确保个性化信息不被后续对话淹没。

**③ 滑动窗口压缩**

当 messages 超过 20 条时，`ContextCompressionNode` 调用 LLM 对早期 14 条消息生成 3-5 句摘要，用 1 条 SystemMessage 替换，保留最近 6 条原始消息。

原理：LLM 的注意力分布在长序列中会衰减，距离当前问题越远的消息，其影响越弱。将无关的早期对话压缩为摘要，既节省 token（实测减少约 72% 的早期消息 token 消耗，样本为 14 轮对话共 28 条消息，比例随对话内容与长度变化；详见 `docs/08` §6.1），又确保关键历史信息（如已预约的服务名、记录编号）不丢失。

**④ RAG 知识库注入**

将 RAG 检索结果作为工具调用结果注入 messages，构成 LLM 回答的事实依据。LLM 的回答从"根据训练知识推断"变为"基于当次检索事实作答"。

**⑤ 跨 Agent userId 传递**

Supervisor 将 userId 以 `<userId>10001</userId>` XML 标签形式嵌入用户消息末尾，子 Agent 的 `MemoryInjectNode` 从文本中解析提取。

这种设计绕开了 A2A 协议的修改成本：不需要修改 AgentCard 或 gRPC 消息格式，只需约定消息末尾的标签格式，即可在整个调用链中无损传递用户身份信息。

**Context 工程的核心价值**：将 Agent 从"无状态函数"升级为"有记忆、有身份感知、有上下文连续性"的对话系统。

## 四、Harness 工程

### 引入前的问题

一个没有评测体系的 Agent 系统面临"黑箱迭代"困境：

1. **无法量化质量**：改了一个 Prompt 之后，效果是变好了还是变差了？没有数据支撑，只能凭感觉判断
2. **回归测试缺失**：修复一个场景的问题，可能悄悄引入另一个场景的 Bug（如为修复路由问题调整了 Prompt，但破坏了工具选择逻辑）
3. **问题发现滞后**：系统上线后，用户实际使用中的问题（如满意度持续下降）无法被及时感知
4. **无基准数据**：新版本与旧版本的性能对比无从进行

### 引入后的效果

Harness 工程建立了"评测数据 → 自动运行 → 结构化结果 → 质量量化 → 条件告警"的完整闭环。

**① 校园 Golden Set（30 条标准用例）**

三类场景各 10 条，每条用例包含：预期路由 Agent、预期工具调用顺序、预期回答关键词、是否需要澄清等维度。

作用：将"这个回答对不对"从主观判断转化为客观检测。运行一批 Golden Set，统计关键词命中率（RAG 召回质量）、路由准确率（Supervisor 决策质量）、工具调用顺序（流程完整性），生成可对比的数值指标。

> ⚠️ **现状说明（2026-08-05）**：当前仓库仅有 Golden Set 数据文件（30 条，三类各 10 条），**尚未实现运行执行器（GoldenSetRunner）**，"量化三维准确率"能力尚未落地。执行器实现计划见 `docs/07-verification-test-plan.md` §6。另注意 consult 场景用例不含 `user_id` 字段（仅 4 字段），与 `docs/05` §3.1 的字段说明不完全一致。

**② 自动化评价分析流水线**

基于 `EvaluationAgentConfiguration` 的批处理 Graph，从数据库拉取真实用户反馈记录，批量运行 `EvaluationClassifierNode` 逐条评分：

- 对每条反馈记录：判断是否为投诉（yes/no）、打满意度分（0-5）、提炼核心诉求
- 汇总：统计投诉率、平均满意度、高频诉求关键词

关键设计是 `BeanOutputConverter<EvaluationResult>`：保证 LLM 输出可被程序解析（不是自由文本），满意度数值可被代码直接用于阈值比较，投诉率可被直接累计统计。如果没有结构化输出，评测结果就只是一堆文字，无法量化，无法触发告警。

**③ 条件分支告警**

`addConditionalEdges` 实现阈值判断：平均满意度 ≥ 3.0 走普通报告路径，< 3.0 走专项告警路径（红色格式，标注【紧急】标识推送钉钉）。

原理：将人工监控替换为自动化监控，系统质量出现异常时（满意度骤降至 3.0 以下），相关人员在第一时间收到通知，将问题响应时间从"下次人工 review 时发现"压缩到"问题发生后数分钟内"。

**Harness 工程的核心价值**：让 Agent 系统的质量从"不可测"变为"可量化、可追踪、可告警"，是从 Demo 走向生产的必要基础设施。

## 五、Loop 工程

### 引入前的问题

一个没有 Loop 能力的 Agent 是"一问一答"的：

1. **无法处理周期性任务**：每天生成运营日报、每周分析用户反馈，这类任务需要人工触发，效率低且容易遗漏
2. **单次执行脆弱**：工具调用失败时，整个任务直接报错返回，没有重试机会
3. **信息不完整时无法追问**：用户说"帮我预约一下"，Agent 要么猜测服务名称（可能猜错）要么直接报错（体验差），无法像人工客服一样继续追问
4. **批量任务无法处理**：对 100 条反馈记录逐一评分，用单次 LLM 调用无法完成（token 限制），需要循环处理

### 引入后的效果

Loop 工程通过六种循环机制将 Agent 从"单次响应"升级为"持续自主运行"的系统。

**① 定时循环（@Scheduled + XxlJob）**

`LocalScheduledTrigger` 将日报 Agent 和评测 Agent 注册为 Spring 定时任务，每天 09:00 自动触发日报生成，每周一 10:00 自动触发用户评价分析。

原理：Spring `@Scheduled` 在独立线程中按 Cron 表达式周期唤醒，调用 `compiledGraph.invoke(Map.of())`，Graph 自动执行完整流水线后结束。这将人工触发的操作成本从"每次几分钟手动操作"降低到"配置一次，永久自动运行"。

**② IterationNode 批量迭代循环**

面对 N 条待分析的反馈记录，`IterationNode` 将其分解为 N 次子图执行，每次子图处理单条记录，将结果累积到输出数组。

原理：将"对 N 个元素做同样的事"这一模式封装为 Graph 节点，屏蔽循环控制逻辑。如果单条记录分析失败，不影响其他记录的处理，最终结果数组中该条记录会有对应的错误标记，整体任务不中断。

**③ 条件分支循环（Adaptive Loop）**

评测完成后根据满意度计算结果决定走告警分支还是普通分支，不同分支的后续 Prompt 和格式不同。

这是 Loop 工程的"自适应"特性：Agent 根据上一步的输出结果决定下一步的行为方向，而非固定走同一条路径。平均满意度从 3.5 降至 2.8，系统行为自动从"普通汇报"切换为"紧急告警"，无需人工判断。

**④ 工具调用 Retry（容错循环）**

`ExecutorNode` 的每个工具调用步骤都包含指数退避重试逻辑：失败后等待 500ms 重试，最多 3 次（延迟分别为 500ms、1000ms、1500ms）。

原理：网络抖动、MySQL 短暂不可用、MCP Server 重启等瞬时故障，通常在几百毫秒内恢复。引入 Retry 后，这类瞬时故障对用户不可见（第一次失败后悄默重试成功），服务可用率从"网络偶发抖动即失败"提升到接近 99%。

**⑤ Human-in-the-Loop（中断-确认-恢复循环）**

`CompileConfig.interruptBefore("executor")` 在 PlannerNode 生成计划后插入暂停点：Agent 先将计划摘要推送给用户，用户确认后 `/confirm?action=approve` 让 Graph 从 Checkpoint 恢复并继续执行。

原理：写操作（预约创建、记录取消）是不可逆的，一旦执行就需要代价才能撤销。HITL 将"不可逆的执行决策权"从 Agent 转移到用户手中，Agent 负责规划，用户负责授权。这是在 AI 置信度无法达到 100% 的阶段，确保系统安全性的关键机制。

**⑥ 多轮澄清循环（信息补全循环）**

当用户信息不完整时（如"帮我预约"缺少服务名称），`PlannerNode` 输出 `needsClarification=true` 和澄清问题，Controller 检测到后立即返回追问，等待用户补充后重新规划。

原理：人工客服面对模糊请求时会追问，而不是猜测或报错。多轮澄清 Loop 赋予 Agent 相同能力。从用户体验角度看，收到"您想预约哪项服务？"比收到"参数错误，服务名称不能为空"的体验好 10 倍。

**Loop 工程的核心价值**：将 Agent 从"被动响应单次请求"升级为"主动执行复杂任务、自主处理异常、持续监控系统状态"的自主智能体。

## 六、长期记忆（Mem0）

### 引入前的问题

一个没有长期记忆的 Agent 存在"金鱼记忆"问题：

1. **每次对话归零**：用户上周告诉 Agent "我喜欢线上办理，下午5点预约"，本周再次使用时 Agent 完全不记得，仍然询问用户偏好
2. **个性化服务缺失**：所有用户得到相同模板化的回答，无法根据用户历史关注点调整回答侧重
3. **重复信息收集**：每次预约都需要用户重新说明偏好，体验割裂
4. **关注点丢失**：用户本学期一直在关注奖学金申请，但 Agent 每次都需要从头解释，无法在用户再次询问时主动带出相关提醒

**会话内 Checkpoint 的局限**：`MemorySaver` 保存的是当次会话状态，关闭浏览器/更换设备后记忆消失。长期记忆（Mem0）解决的是跨会话、跨设备的持久化问题。

### 引入后的效果

长期记忆通过三个阶段形成"学习 → 记住 → 应用"的完整闭环：

**① 记忆写入（memory-store）**

当对话中出现明确的长期偏好信号时，Agent 调用 `memory-store` 工具异步写入 Mem0：

```
用户说："我一般下午5点以后才有空，预约时尽量安排晚上"
→ order-agent 调用 memory-store：
   userId=10001, content="用户偏好下午/晚上预约，时间偏好为晚上"
```

写入采用异步方式（`@Async`），不阻塞当前对话流程，对用户无感知，完成后仅记录日志。

**② 记忆检索（memory-search）**

`MemoryInjectNode` 在每次对话前主动查询 Mem0 的 `/v2/memories/search/` 接口：

```
查询参数：{
  "query": "用户偏好和历史习惯",
  "user_id": "10001",
  "filters": {"created_at": {"gte": "两周前", "lte": "明天"}}  // 查询近两周记忆
}
```

Mem0 对存储的记忆进行语义检索，返回与当前 query 最相关的历史偏好记录。检索时间窗口限制在两周内，确保使用的是较近期的偏好，避免久远记忆（用户状态可能已改变）干扰当前决策。

**③ 记忆注入与应用**

检索结果以 `SystemMessage` 形式注入当次对话上下文：

```
SystemMessage: "【用户历史偏好记忆】
该用户偏好线上办理，常在下午5点后预约，
主要关注图书馆研讨间和奖学金政策。"
```

Agent 在此上下文下生成回答时，会自然地：
- 建议预约时选择"线上"方式，时间选"下午/晚上"
- 回答奖学金问题时主动关联用户历史关注点
- 不再重复询问用户已经告知过的偏好信息

**长期记忆的工作原理示意**：
```
第 1 次对话（周一）：
  用户："预约图书馆，晚上8点"
  Agent 执行预约 → 记录偏好"用户偏好晚上预约图书馆" → 写入 Mem0

第 5 次对话（周五，不同会话）：
  Memory 注入：读取到"偏好晚上预约图书馆"
  用户："帮我再预约一次图书馆"
  Agent（有记忆）："为您预约图书馆研讨间，时间偏好晚上，已自动选择。请确认日期。"
  Agent（无记忆）："请问您的预约时间偏好是？"
```

**长期记忆的核心价值**：将 Agent 从"每次都是陌生人"升级为"了解用户、越用越懂的助理"，是个性化服务体验的核心基础。服务使用频率越高、时间越长，记忆越丰富，个性化效果越显著。

## 总结

| 能力 | 解决的核心问题 | 引入后的本质变化 |
|------|-------------|--------------|
| **RAG** | LLM 知识局限与幻觉 | 从"凭记忆猜答案"变为"基于文档事实作答" |
| **Prompt 工程** | LLM 行为不可控 | 从"自由发挥"变为"在约束范围内精确执行" |
| **Context 工程** | 上下文割裂与丢失 | 从"无状态函数"变为"有记忆、有身份感知的连续系统" |
| **Harness 工程** | 系统质量不可量化 | 从"靠感觉判断好坏"变为"数据驱动的可量化迭代" |
| **Loop 工程** | 单次响应的局限 | 从"被动一问一答"变为"主动、持续、自适应的自主执行" |
| **长期记忆** | 跨会话遗忘 | 从"每次都是陌生人"变为"越用越懂用户的个性化助理" |
